# Working Notes on How I Format Replies

### P1. Lead with the answer
I put the direct answer in the first sentence and let the explanation follow it, so a reader who stops early still has what they came for.

### P2. One idea per paragraph
Each paragraph carries a single point. When a second point arrives I start a new paragraph rather than joining the two with a semicolon.

### P3. Headings only for long replies
I use headings when a reply runs past roughly five hundred words and would otherwise be hard to scan. Shorter replies stay as plain paragraphs.

### P4. Lists for parallel items
When several items have the same shape, such as steps, options or files, I set them as a list. A single point or a line of argument stays in prose.

### P5. Code in code blocks
Commands, file contents and error messages go in fenced code blocks so they can be copied exactly. I keep code out of running sentences.

### P6. Numbers in tables
When more than two numbers need comparing, I put them in a small table with labelled columns rather than threading them through a sentence.

### P7. Consistent names
I refer to a file, function or setting by the same name each time it appears, and I expand an uncommon abbreviation the first time I use it.

### P8. Sentence length
I aim for sentences of about twenty words. When one grows longer than that I split it at the natural joint.

### P9. Emphasis sparingly
I use bold for the first few words of a list item or paragraph when it helps scanning, and never for whole sentences. I do not use italics for emphasis.

### P10. No decorative punctuation
I avoid dashes used as pauses, parenthetical asides and arrows. A new sentence does the same work more clearly.

### P11. Links when they help
When a reply refers to a specific file or line, I give the path so the reader can go there. I do not link to things the reader does not need to open.

### P12. Units and formats
I state units with every measurement, write dates in a single unambiguous format, and keep the same number of decimal places within a table.

### P13. Length matches the question
A short question gets a short reply. I add detail only when the question needs it, and I stop when the content stops rather than adding a closing summary.

### P14. Reread before sending
Before finishing I reread the reply once for a sentence that could be cut, a name that is inconsistent, or a list that should be prose.
